# 🔐 Authentication & Security Architecture
**Project:** EduBharat AI
**Specification:** Role-Based Access Control (RBAC) & Security Lifecycle

## 1. Security Overview
EduBharat AI handles multi-stakeholder school operations across 4 distinct user profiles: Students, Teachers, Principals, and Parents. To maintain strict data boundaries, the architecture enforces dedicated role privilege tiers, separating academic views from administrative controls.

## 2. Role-Based Access Control (RBAC) Matrix

| Resource / Action | Student | Teacher | Principal | Parent |
|---|---|---|---|---|
| View Study Materials & AI Notes | Read | Read | Read | Read |
| View Personal Test Scores | Read (Own) | Read (Class) | Read (All) | Read (Ward) |
| Submit Student Doubts | Execute | No Access | No Access | No Access |
| Take / Edit Class Attendance | No Access | Read / Write | Read / Write | No Access |
| Evaluate Papers & Upload Marks | No Access | Read / Write | Read / Write | No Access |
| School-Wide Notice Broadcast | No Access | No Access | Read / Write | No Access |
| Institutional Analytics | No Access | No Access | Read / Write | No Access |
| View Fee & Attendance Status | Read (Own) | Read (Class) | Read (All) | Read (Ward) |

## 3. v1.0 Prototype Client-Side State Isolation
* **Zero Backend Infiltration:** In the v1.0 offline prototype, authorization is simulated using client-side JavaScript state switches (`switchView(roleId)`).
* **State Reset On Navigation:** Whenever a user returns to the Gateway view or clicks "Logout", the session variable is flushed to prevent state bleeding between roles.
* **Scope Disclaimer:** The client-side toggle satisfies proof-of-concept and UI demonstration goals. It is strictly designated as an offline MVP prototype.

## 4. Production Security Architecture (v2.0 Transition)

### 4.1 Identity Provider & Token Flow
* **Authentication Engine:** Google Firebase Authentication integrating Phone OTP (for parents/teachers) and Student ID credentials.
* **Token Standard:** JSON Web Tokens (JWT) signed via RS256 algorithm.
* **Claims Handling:** User roles (`student`, `teacher`, `principal`, `parent`) are encoded directly inside Custom Claims within the JWT payload.

### 4.2 Data Layer Security Rules
* **Database Guardrails (Firestore Security Rules):**
  ```javascript
  rules_version = '2';
  service cloud.firestore {
    match /databases/{database}/documents {
      // Principal has global read/write access
      match /{document=**} {
        allow read, write: if request.auth.token.role == 'principal';
      }
      // Teachers manage their assigned class only
      match /attendance/{classId}/{document=**} {
        allow read, write: if request.auth.token.role == 'teacher' && 
                              request.auth.token.classId == classId;
      }
      // Students can only access their personal records
      match /students/{studentId}/{document=**} {
        allow read: if request.auth.uid == studentId;
      }
    }
  }
  ```

### 4.3 Data Privacy Compliance
* Strict alignment with Indian digital personal data protection standards regarding student educational records.
* Complete sanitization of form inputs to prevent XSS (Cross-Site Scripting) during teacher evaluations and broadcast circular entries.
